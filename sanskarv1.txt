PART 1 — PROJECT OVERVIEW
-------------------------------------------------------------------------------

[What is this project?]
This project is packaged as an end-to-end MLOps platform designed for cybersecurity vulnerability management. It ingests software vulnerability data (CVEs) from sources like NVD (National Vulnerability Database), CISA KEV (Known Exploited Vulnerabilities), and EPSS (Exploit Prediction Scoring System), trains an XGBoost classifier to predict CVSS base severity ratings (NONE, LOW, MEDIUM, HIGH, CRITICAL), and calculates a composite risk score (0–100) to prioritize remediation actions. It provides a FastAPI backend, an HTML/JS executive web dashboard, Airflow DAGs for pipeline orchestration, and MLflow for experiment tracking.

[What real-world problem is it solving?]
Modern enterprise security teams face thousands of newly published Common Vulnerabilities and Exposures (CVEs) every month. Security analysts cannot patch every vulnerability immediately. Raw CVSS base scores alone do not reflect real-world threat context (e.g., whether an exploit is actively being used in the wild or whether the affected asset is internet-facing). This project attempts to combine machine learning predictions with threat intelligence (EPSS, CISA KEV) and asset metadata (criticality, exposure) to prioritize which vulnerabilities pose the highest immediate risk.

[What is the exact objective?]
1. Predict the CVSS base severity class (NONE, LOW, MEDIUM, HIGH, CRITICAL) using machine learning trained on CVSS submetrics, text keywords, CWE IDs, and metadata.
2. Calculate a composite risk prioritization score (0–100) and assign SLA remediation tiers (CRITICAL_RISK, HIGH_RISK, MEDIUM_RISK, LOW_RISK).
3. Provide an MLOps pipeline with data validation, model tracking, drift monitoring, and retraining capabilities.

[Who would use it?]
Security Operations Center (SOC) analysts, Vulnerability Managers, IT Security Engineering teams, and Chief Information Security Officers (CISOs).

[What is the input?]
- Vulnerability records containing: CVE ID, description text, CVSS vector string (e.g. CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H), publication date, CWE IDs, vendor counts, and reference URLs.
- Threat intelligence signals: EPSS score (probability 0–1), CISA KEV listing status (boolean).
- Asset context: Asset criticality multiplier (0.0–1.0 or Tier 1–3) and network exposure level (internet-facing, internal, air-gapped).

[What is the output?]
- Predicted CVSS severity class (NONE, LOW, MEDIUM, HIGH, CRITICAL) with calibrated class probabilities and confidence score.
- SHAP feature contribution waterfall (explaining why a prediction was made).
- Composite risk priority score (0.0 to 100.0) with an assigned SLA tier (CRITICAL_RISK, HIGH_RISK, MEDIUM_RISK, LOW_RISK) and component breakdown.
- Visual dashboard metrics, Prometheus metrics, and drift reports.

[What is the complete flow from input to final result?]
1. Data Ingestion: NVD API / CISA KEV / EPSS or synthetic dataset generator (`scripts/seed_data.py`) creates raw vulnerability data.
2. Data Validation: `DataValidator` checks raw records against Pandera schemas for formatting and range constraints.
3. Feature Engineering: `FeatureEngineer` parses CVSS vector strings into 22 binary one-hot features, extracts text keyword flags, formats CWE categories, and adds temporal features.
4. Model Training: `SeverityClassifier` fits an XGBoost classifier on SMOTE-balanced training data, calibrates probabilities using Isotonic Regression, and logs metrics to MLflow via `VulnerabilityTrainer`.
5. Quality Gate: `ModelQualityGate` verifies macro F1, critical recall, ECE, and latency against thresholds.
6. Risk Scoring: `RiskScorer` combines predicted severity, EPSS, CISA KEV, asset criticality, and exposure into a final score (0–100).
7. Serving & Visualization: FastAPI REST API (`src/serving/api/main.py`) exposes `/predict`, `/risk-score`, and `/explain` endpoints, consumed by the dashboard frontend (`src/dashboard/index.html`).
8. Monitoring & Retraining: `DriftMonitor` computes Population Stability Index (PSI) and KS-test statistics on incoming feature data, intended to trigger Airflow retraining DAGs upon drift detection.

[How does it relate to the topic: "Adaptive MLOps for Software Vulnerability Detection and Risk Prioritization"?]
- Vulnerability Detection: CLAIMED in the title/README, but NOT IMPLEMENTED in the code (it does not perform code scanning, AST analysis, or vulnerability discovery).
- Risk Prioritization: IMPLEMENTED via a composite weighted scoring formula.
- Adaptive MLOps: CLAIMED via automated drift monitoring and Airflow retraining DAGs, but BROKEN in implementation due to code mismatches and missing methods.

[Explanations by Length]
- 2–3 Sentences Explanation:
  This project is a vulnerability risk scoring and severity classification platform built with Python, XGBoost, FastAPI, and Docker. It ingests CVE data from NVD, CISA KEV, and EPSS, predicts CVSS severity levels using structured features and text keywords, and computes a composite risk score (0–100) to help security teams prioritize patching. - 30-Second Explanation:
  This project builds a machine learning pipeline that takes software vulnerability data and threat intelligence feeds to output an actionable risk score between 0 and 100. It uses XGBoost with isotonic calibration to classify severity into 5 tiers, explains predictions using SHAP, and combines prediction confidence with CISA KEV active exploit data, EPSS probabilities, and asset criticality. It features a dark-mode web dashboard and FastAPI serving layer. However, while the project presents an impressive UI and dockerized stack, deep inspection reveals that key MLOps components like automated retraining DAGs and several API endpoints use broken code or hardcoded mock responses rather than real dynamic execution.

- Detailed Technical Explanation:
  The codebase implements a multi-class ordinal classifier (XGBoost 5-class softprob) aimed at predicting CVSS v3.1 base severity from parsed vector components (Attack Vector, Attack Complexity, Privileges Required, etc.), NLP description regex matches, CWE groupings, and metadata. The pipeline attempts to avoid target leakage by explicitly excluding the CVSS base score from input features, using only submetric flags. Training incorporates SMOTE oversampling for class balance and Isotonic Regression for probability calibration. Model artifacts and evaluation metrics are managed via MLflow tracking and evaluated against a Quality Gate enforcing Macro F1 >= 0.82 and Critical Recall >= 0.88. Serving is handled by a FastAPI application with endpoints for inference, SHAP tree explanations, and risk scoring. Pipeline orchestration is defined via Apache Airflow DAGs, and statistical drift monitoring is implemented using Kolmogorov-Smirnov and Population Stability Index (PSI) tests. However, multiple critical integration failures exist: Airflow DAGs and execution scripts call non-existent methods and modules, API endpoints for drift and model registry return static mock JSON, and the synthetic dataset generator creates template-based data that invalidates temporal cross-validation.

PART 2 — PROBLEM DEFINITION
-------------------------------------------------------------------------------

A. Vulnerability Detection (Identifying unknown bugs/flaws in code or binaries):
   - CLAIMED IN TITLE & README: Yes ("Software Vulnerability Detection").
   - ACTUALLY PERFORMED: NO. There is no static analysis (SAST), dynamic analysis (DAST), binary auditing, or code scanning logic in the repo. The system ingests already known CVEs.

B. Vulnerability Exploitation Prediction (Predicting if a CVE will be exploited in the wild):
   - ACTUALLY PERFORMED: NO (by ML model). Exploitation probability is NOT predicted by the system's ML model. Instead, the project imports external EPSS scores (Exploit Prediction Scoring System by FIRST.org) and CISA KEV catalog flags directly as raw inputs.

C. Vulnerability Risk Scoring (Calculating a numerical risk metric based on severity and context):
   - ACTUALLY PERFORMED: YES. Implemented in `src/models/risk_scorer.py` (`RiskScorer` class). It combines ML-predicted severity, EPSS probability, CISA KEV status, asset criticality, and network exposure into a 0–100 score.

D. Vulnerability Prioritization (Ranking vulnerabilities and mapping to remediation SLAs):
   - ACTUALLY PERFORMED: YES. The composite risk score is mapped into 4 risk tiers (CRITICAL_RISK, HIGH_RISK, MEDIUM_RISK, LOW_RISK) associated with SLA remediation timeframes (24h, 72h, 14 days, 30 days).

[Summary of Discrepancies between Claims and Reality]:
- Major Misleading Claim: The title and README state "Vulnerability Detection". A security reviewer will immediately notice that the system does not detect vulnerabilities. It should be titled "Vulnerability Severity Classification and Risk Prioritization".
- Exploitation Claim: The README implies the system assesses exploitation risk, but it merely ingests third-party EPSS scores and CISA KEV flags as passive inputs.

PART 5 — DATASET / DATA SOURCES
-------------------------------------------------------------------------------

Dataset Name: `vulnerabilities_dataset.csv` / `vulnerabilities_dataset.parquet`
Primary Source in Repo: Generated by `scripts/seed_data.py`.
Referenced External Sources:
- NIST NVD 2.0 API (`https://services.nvd.nist.gov/rest/json/cves/2.0`)
- CISA Known Exploited Vulnerabilities Catalog (`https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`)
- FIRST EPSS API (`https://api.first.org/data/v1/epss`)

Sample Count: 500 rows in committed data (default `seed_data.py` generates 3,000 rows).
Features / Columns: 18 raw columns, transformed into 40+ engineered features.
Target Variable: `base_severity` (raw string label: NONE, LOW, MEDIUM, HIGH, CRITICAL), transformed to `severity_numeric` (0 to 4 ordinal).

Feature Breakdown and Usage:
1. CVSS Vector String (`cvss_vector_string`): e.g. "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H". Parsed by `cvss_parser.py` into 22 binary one-hot features (`av_network`, `ac_low`, `pr_none`, `ui_none`, `scope_changed`, `ci_high`, etc.). Used as primary features for severity prediction.
2. Description (`description`): Raw vulnerability text. Used in `feature_engineer.py` to extract `description_length`, `description_word_count`, and boolean keyword flags (`has_rce_keyword`, `has_sqli_keyword`, `has_xss_keyword`, `has_overflow_keyword`, `has_auth_bypass_keyword`, `has_priv_esc_keyword`, `has_dos_keyword`).
3. Publication Date (`published_date`): ISO timestamp. Used for `TemporalCrossValidator` time-ordering and feature derivation (`days_since_published`, `quarter_published`, `year_published`, `is_recent`).
4. CISA KEV (`cisa_kev` / `in_cisa_kev`): Boolean flag indicating active exploitation in the wild listed in CISA's catalog. Used as an exploitation feature in ML and as a 25% weighted component in risk scoring.
5. EPSS Score (`epss_score`): Float between 0.0 and 1.0 representing the FIRST.org empirical probability of exploitation in the next 30 days. Used as an exploitation feature in ML and as a 15–20% weighted component in risk scoring.
6. EPSS Percentile (`epss_percentile`): Float between 0.0 and 1.0 representing relative EPSS rank. Used as a feature in ML.
7. CWE IDs (`cwe_ids`): Common Weakness Enumeration identifiers (e.g. CWE-79, CWE-89). Mapped into broad category booleans (`is_memory_safety_cwe`, `is_injection_cwe`, `is_auth_cwe`, `is_config_cwe`) and primary category ID.
8. Vendor Count & Reference Count (`vendor_count`, `reference_count`): Integer counts of affected CPEs and reference URLs. Used as metadata complexity features.
9. Asset Criticality (`asset_criticality`): Float between 0.0 and 1.0 (or multiplier 0.8x to 1.3x) representing organizational asset importance. Used exclusively in `RiskScorer` formula (NOT ML model).
10. Network Exposure (`exposure_score` / `asset_exposure`): Float between 0.0 and 1.0 (or level: internet-facing, internal, air-gapped). Used exclusively in `RiskScorer` formula.

Missing Values: Raw missing text/scores are coerced to empty strings / 0.0 / median values in preprocessing.
Class Distribution in Seed Data: Roughly 35% MEDIUM, 30% HIGH, 20% CRITICAL, 15% LOW.
Splits: 70% Train, 15% Validation, 15% Test via `TemporalCrossValidator`.
Time Period Covered: Synthetic dates span 2021 to 2025.
Data Dynamicity: Static seed dataset provided. External API clients exist but are not dynamically synced to a live database during execution.

PART 6 — MACHINE LEARNING
-------------------------------------------------------------------------------

ML Problem Formulation:
- Type: 5-Class Ordinal Classification.
- Target: `severity_numeric` (0=NONE, 1=LOW, 2=MEDIUM, 3=HIGH, 4=CRITICAL).
- Inputs: 22 CVSS one-hot submetrics, 4 temporal features, 4 exploitation features, 9 text keyword/length features, 5 CWE category features, 3 metadata features. Total: 47 features.
- Model Algorithm: XGBoost (`XGBClassifier`) with parameters: `n_estimators=500`, `max_depth=6`, `learning_rate=0.05`, `subsample=0.8`, `colsample_bytree=0.8`, `objective='multi:softprob'`, `tree_method='hist'`.
- Model Calibration: `CalibratedClassifierCV` using Isotonic Regression fitted on validation fold or via 5-fold CV.
- Imbalance Strategy: `SMOTE` (Synthetic Minority Over-sampling Technique) applied to training features.
- Model Choice Rationale: XGBoost handles mixed tabular feature types (booleans, integers, floats) well, provides high gradient boosting performance, and integrates natively with SHAP `TreeExplainer`.

Complete ML Pipeline Flow (as coded in `trainer.py`):
1. Raw Data -> `DataValidator.validate_raw()` (cleans duplicates, checks schema).
2. `FeatureEngineer.transform()` -> extracts submetrics, keywords, CWEs, temporal signals.
3. Filtering -> drops records missing target labels.
4. `TemporalCrossValidator.temporal_split()` -> sorts by `year_published` and splits 70/15/15.
5. Imbalance Handling -> `SMOTE.fit_resample()` balances minority classes in training set.
6. Scaling & Model Fit -> `StandardScaler` + `XGBClassifier.fit()` with early stopping on validation set.
7. Probability Calibration -> `CalibratedClassifierCV(method='isotonic')` fits on validation set.
8. Test Evaluation -> calculates Macro F1, Weighted F1, Critical Recall, ROC-AUC, ECE (Expected Calibration Error), p99 latency.
9. SHAP Analysis -> `SHAPExplainer` computes per-sample waterfall and global mean |SHAP| values.
10. MLflow Tracking -> logs parameters, metrics, feature importance artifacts, and registered model.
11. Quality Gate -> `ModelQualityGate.evaluate()` checks criteria before promotion.


-------------------------------------------------------------------------------
PART 7 — MODEL EVALUATION
-------------------------------------------------------------------------------

Evaluation Metrics Implemented:
1. Macro F1 Score: Unweighted average of F1 across all 5 classes. Primary quality gate metric (threshold >= 0.82).
2. Critical Class Recall: Recall specifically for Class 4 (CRITICAL). Secondary quality gate metric (threshold >= 0.88).
3. Expected Calibration Error (ECE): Measures calibration alignment between predicted probabilities and empirical accuracy across 10 bins. Threshold <= 0.10.
4. ROC-AUC: One-vs-Rest macro-averaged ROC-AUC across all 5 classes.
5. Balanced Accuracy: Macro-averaged recall across all classes.
6. Inference Latency (p99): 99th percentile inference time in milliseconds (threshold <= 50ms).
7. Confusion Matrix: 5x5 confusion matrix.

Critical Analysis of Evaluation Results:
- High Reported Accuracy / F1 (~0.89+):
  The repository reports a high Macro F1 of 0.894 and Critical Recall of 0.941. HOWEVER, this result is misleading due to the dataset generation method:
  `scripts/seed_data.py` generates synthetic data by randomly picking from a tiny list of 8 fixed template dictionaries (`SAMPLE_VULNERABILITIES`). Out of 3,000 generated records, all 3,000 are simple noisy duplicates of these 8 templates. As a result, the training, validation, and test sets contain virtually identical feature vectors. The high F1 score is an artifact of synthetic data repetition, NOT real-world generalization performance.
- Evaluation Metric Appropriateness:
  - Macro F1 and Critical Recall are highly appropriate for severity classification because missing a CRITICAL vulnerability has severe real-world security consequences.
  - ECE is an excellent metric for risk scoring because raw uncalibrated probabilities from tree models produce extreme 0/1 estimates.
  - MISSING METRICS: For risk prioritization (ranking CVEs by risk score), the project completely lacks ranking evaluation metrics such as NDCG (Normalized Discounted Cumulative Gain), MAP (Mean Average Precision), or Precision@K.

PART 8 — SECURITY LOGIC
-------------------------------------------------------------------------------

How the System Determines Risk:
Risk determination uses a hybrid approach:
1. ML Prediction: Predicts the CVSS severity class (NONE, LOW, MEDIUM, HIGH, CRITICAL) and maps it to a normalized severity score ($S_{\text{norm}} \in [0.0, 1.0]$: NONE=0.0, LOW=0.2, MEDIUM=0.5, HIGH=0.78, CRITICAL=1.0).
2. Weighted Linear Formula: Combines ML severity, CISA KEV flag, EPSS score, asset criticality, network exposure, and model confidence using a weighted sum.

Actual Formula in Code (`src/models/risk_scorer.py`):

$$\text{Raw Score} = w_{\text{cvss}} \cdot S_{\text{norm}} + w_{\text{kev}} \cdot K + w_{\text{epss}} \cdot P_{\text{epss}} + w_{\text{crit}} \cdot C_{\text{asset}} + w_{\text{exp}} \cdot E_{\text{net}} + w_{\text{conf}} \cdot \text{Conf}$$

$$\text{Risk Score} = \text{round}(\text{Raw Score} \times 100, 2)$$

Where default code weights (summing to 1.0) are:
- $w_{\text{cvss}} = 0.30$ (Predicted Severity)
- $w_{\text{kev}} = 0.25$ (CISA KEV active: 1.0 if True, 0.0 if False)
- $w_{\text{epss}} = 0.20$ (EPSS exploitation probability: 0.0 to 1.0)
- $w_{\text{crit}} = 0.15$ (Asset Criticality: 0.0 to 1.0, default 0.5)
- $w_{\text{exp}} = 0.07$ (Network Exposure: 0.0 to 1.0, default 0.5)
- $w_{\text{conf}} = 0.03$ (Model Confidence: 0.0 to 1.0)

Risk Tiers & Remediation SLAs:
- Score >= 90.0: CRITICAL_RISK (SLA: 24 hours)
- Score >= 70.0: HIGH_RISK (SLA: 72 hours)
- Score >= 40.0: MEDIUM_RISK (SLA: 14 days)
- Score < 40.0: LOW_RISK (SLA: 30 days)

Hypothetical Calculation Example:
Consider CVE-2024-LOG4J:
- Predicted Severity: CRITICAL (Class 4 -> $S_{\text{norm}} = 1.0$)
- Model Confidence: 0.95
- CISA KEV: Active ($K = 1.0$)
- EPSS Score: 0.90 ($P_{\text{epss}} = 0.90$)
- Asset Criticality: Tier 1 Core Production ($C_{\text{asset}} = 1.0$)
- Network Exposure: Public Internet-Facing ($E_{\text{net}} = 1.0$)

$$\text{Raw Score} = (0.30 \times 1.0) + (0.25 \times 1.0) + (0.20 \times 0.90) + (0.15 \times 1.0) + (0.07 \times 1.0) + (0.03 \times 0.95)$$
$$\text{Raw Score} = 0.30 + 0.25 + 0.18 + 0.15 + 0.07 + 0.0285 = 0.9785$$
$$\text{Risk Score} = 97.85 \longrightarrow \mathbf{CRITICAL\_RISK}$$

CRITICAL DOCUMENTATION DISCREPANCY:
The README.md presents a DIFFERENT, multiplicative formula containing asset multipliers ($M_{\text{criticality}} = 0.8\text{x--}1.3\text{x}$, $M_{\text{exposure}} = 0.6\text{x--}1.25\text{x}$). However, `risk_scorer.py` implements a strictly linear additive weighted sum of 6 normalized components. The README formula does NOT exist in the Python code.

PART 11 — DRIFT DETECTION
-------------------------------------------------------------------------------

Monitored Elements:
- Numerical Features: `epss_score`, `cvss_exploitability_score`, `cvss_impact_score`, `description_length`, `token_count`.
- Categorical Features: `attack_vector`, `attack_complexity`, `privileges_required`, `user_interaction`, `scope`.

Statistical Methods Implemented (`src/monitoring/drift_detector.py`):
1. Kolmogorov-Smirnov 2-Sample Test (KS-Test): Measures distribution shift for numerical variables (significance level $\alpha = 0.05$).
2. Population Stability Index (PSI): Measures population shift across 10 quantile bins (threshold PSI > 0.20 indicates significant drift).
3. Chi-Square Test: Measures frequency shift for categorical variables.

Thresholds & Baselines:
- Significance Level ($\alpha$): 0.05
- PSI Threshold: 0.20
- Drift Share Threshold: 0.25 (if >25% of features drift, dataset drift is declared).
- Reference Dataset: Baseline training features saved at `data/processed/features.parquet`.
- Current Dataset: Production inference logs.

Missing / Discrepant Integration:
README.md and `requirements.txt` state that Evidently AI is used for drift monitoring. However, `src/monitoring/drift_detector.py` DOES NOT import or use Evidently AI; it uses a custom SciPy implementation. Furthermore, the API endpoint `/api/v1/drift` returns a hardcoded static dictionary regardless of actual drift.

PART 17 — DATA LEAKAGE INVESTIGATION
-------------------------------------------------------------------------------

1. CVSS Base Score / Severity (Target Leakage):
   - Status: CLEANLY PREVENTED in `feature_engineer.py` and `cvss_parser.py`.
   - Detail: The pipeline explicitly excludes `base_score`, `base_severity`, `exploitability_score`, and `impact_score` from the input feature set (`ALL_FEATURES`). Features are derived solely from vector string submetrics (`av_network`, `ac_low`, etc.), text regex matches, CWEs, and metadata.

2. EPSS Scores & CISA KEV Listings (Temporal Leakage):
   - Status: POTENTIAL TEMPORAL LEAKAGE PRESENT.
   - Investigation:
     "Would EPSS scores and CISA KEV listing status be available at the exact moment a vulnerability is published?"
     Answer: NO.
     - EPSS scores evolve daily based on emerging threat activity over time.
     - CISA KEV listings are added weeks, months, or years AFTER a CVE is published (when active exploitation is observed in the wild).
     - In `feature_engineer.py`, `in_cisa_kev` and `epss_score` are included as features in `ALL_FEATURES` used by `SeverityClassifier`.
     - If the model is evaluated on predicting the severity of a newly published CVE using EPSS scores or KEV flags collected *after* publication, this constitutes **temporal data leakage**.
   - Impact: Model relies on future threat signals to predict initial CVSS severity, which is impossible at publication time.

PART 18 — TEMPORAL VALIDATION
-------------------------------------------------------------------------------

Validation Methodology Evaluation:
- `src/training/cross_validation.py` defines `TemporalCrossValidator`, which sorts records by `year_published` and performs a strict temporal train/validation/test split (70% oldest, 15% middle, 15% newest) or walk-forward CV folds.
- In theory, temporal splitting is the CORRECT methodology for vulnerability prediction because it simulates predicting future CVEs from past historical data without future leakage.
- IN PRACTICE (in this repository):
  `scripts/seed_data.py` generates synthetic publication dates (2021 to 2025) randomly assigned to the 8 static template vulnerabilities. Because the underlying vulnerability templates in 2025 are identical to those in 2021, the temporal split has NO EFFECT on evaluating time-based distribution shifts or concept drift. The evaluation remains flawed despite the time-aware code.

PART 21 — IF WE BUILD OUR OWN VERSION
-------------------------------------------------------------------------------

Proposed Clean Architecture Blueprint:

1. Problem Definition:
   "Adaptive MLOps Platform for CVE Severity Classification & Contextual Risk Prioritization"
   Explicitly separate severity classification (ML task) from risk prioritization (contextual scoring engine).

2. Data Pipeline:
   - Automated ingestion from NVD 2.0 REST API, CISA KEV JSON, and FIRST EPSS API stored in PostgreSQL database.
   - Version raw data snapshots using DVC linked to MinIO (S3) bucket.

3. Feature Engineering:
   - Parse CVSS v3.1 vector strings into 22 binary submetric features.
   - Text features: TF-IDF vectorization (top 300 n-grams) on CVE descriptions + domain keyword flags.
   - CWE hierarchical category mapping.
   - STRICT LEAKAGE GUARD: Exclude EPSS and CISA KEV from severity classification training features; use them ONLY in the post-ML risk prioritization stage.

4. ML Formulation:
   - Target: Ordinal 5-class severity (`NONE`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`).
   - Algorithms: XGBoost / LightGBM baseline vs Fine-Tuned DeBERTa-v3 NLP classifier for description-only records.
   - Calibration: Isotonic Regression to ensure output class probabilities equal empirical accuracy.

5. Evaluation Strategy:
   - Primary Metric: Macro F1 and Critical Class Recall.
   - Calibration Metric: Expected Calibration Error (ECE < 0.08).
   - Validation Split: Time-aware walk-forward temporal cross-validation based on actual CVE publication dates.

6. Risk Prioritization Logic:
   - Non-linear composite risk formula:
     $$\text{Risk Score} = \left( 0.40 \cdot S_{\text{ML}} + 0.35 \cdot P_{\text{EPSS}} + 0.25 \cdot I_{\text{KEV}} \right) \times M_{\text{criticality}} \times M_{\text{exposure}}$$
   - Clamped to $[0, 100]$ and mapped to 4 SLA remediation tiers.

7. MLOps Architecture:
   - Experiment Tracking: MLflow with S3 artifact store and PostgreSQL backend.
   - Orchestration: Apache Airflow DAGs with tested PythonOperators.
   - Model Registry: Champion / Challenger staging with automated Quality Gate enforcement.

8. Drift Detection:
   - Evidently AI data drift reports generated daily comparing 30-day inference window against baseline training distribution.
   - Monitor PSI (>0.20) and Wasserstein distance.

9. Retraining:
   - Automatic Airflow retraining DAG triggered when dataset drift share > 25%.
   - Train challenger model -> evaluate quality gate -> compare champion vs challenger -> promote via MLflow API if challenger exceeds champion F1 by >=1.0%.

10. Deployment & Monitoring:
    - FastAPI serving layer with real-time SHAP explanations.
    - Prometheus metrics exporter tracking latency (p95 < 50ms), throughput, and prediction distributions.
    - Full executive React or HTML/JS dashboard displaying real dynamic metrics.

What Makes it Genuinely "Adaptive MLOps":
1. Automated Feedback Loop: Real analyst label corrections submitted via `/feedback` are stored in PostgreSQL and automatically included as weighted samples in the next retraining run.
2. Automated Drift-Triggered Retraining: Real inference logs trigger retraining without human intervention when feature distributions drift.
3. Champion/Challenger Shadow Evaluation: Challenger model automatically runs in shadow mode on live traffic, comparing real-world latency and agreement before promotion.
